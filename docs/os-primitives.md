# IntentOS OS 原语说明

> OS 原语 = IntentOS 的**内置系统能力**。它们直接映射操作系统 API（内存/进程/文件/磁盘/电源…），是"AI 与 OS 之间"最底层的那一层。只做**高频、安全模型清晰**的系统能力；复杂工具（ffmpeg/数据库等）留给 exec / 插件，不进内核。

**实现说明**：环境无 psutil，全部用 **stdlib + ctypes（Windows API）+ subprocess** 实现，Windows 优先。
交互域里**只有剪贴板那两条**用了 pywin32（`win32clipboard`）；窗口 / 截屏 / 模拟输入 / 通知
都是 ctypes 零依赖 —— 这样即使某台机器装不上 pywin32，大部分交互能力照样能用。

> 📅 更新：2026-09-12 ｜ 原语 24 → **98** —— 能力地图上「建议做原语」的条目**全部落地**。
> 本轮补齐：界面交互与显示、计划任务的写侧、事件日志、电源与系统信息、时区、声音与外设。
> 全程新增九个域：归档 / Shell / 权限 / 环境变量 / 计划任务 / 显示 / 时间 / 声音 / 外设。
> 跨域复用的工具与路径判定已下沉到 `primitives/_common.py` —— 见文末「跨文件复用」。
> `fs.copy` / `fs.move` 改为**需确认**，同时**撤掉了可写白名单** —— 为什么撤、写侧的边界现在靠什么，见「安全约定」里的「写侧的边界」。
>
> **清单表新增「块」列**：98 条按「**操作对象**」归成 13 块（不等同于下面的「域」——
> `acl.get` 归文件块、`sound.beep` 归界面块、`time.zones` 归进程块），供接入方按需展开
> 而不是全量注入。见 README 的「工具分块」一节，或 `python adapters/cli.py blocks`。

### 注册表 / 系统配置域

| 原语 | 作用 | 需确认 | 有 dry_run | 块 |
|------|------|:---:|:---:|:---:|
| `registry.read` | 读注册表（值 + 子键；根键白名单 + 敏感区黑名单 + 分页防爆） | 否 | — | 系统配置 |
| `registry.write` | 写 / 新建 / 删注册表的值或键（硬拒敏感区与自启动键；带 before/after 审计） | **是** | ✅ 默认 True | 系统配置 |
| `startup.list` | 开机自启动清单：注册表 Run/RunOnce + 启动文件夹 + 自启动服务 + 开机/登录任务，一次收齐 | 否 | — | 服务与计划任务 |
| `reg.assoc` | 查文件关联：双击某扩展名实际用哪个程序打开 | 否 | — | 系统配置 |

> **底座之一**：已装软件清单、文件关联（`reg.assoc`）这类「读注册表某几个键」的能力
> 都建在它上面 —— 有了它，这一片就不用各自去碰 `winreg`。
>
> ⚠️ **两个例外**：`startup.list`（要同时扫注册表、文件系统、服务和计划任务）和 `env.*`
> （要同时碰注册表和 `ctypes` 广播 `WM_SETTINGCHANGE`），都是自己碰 `winreg`。
> 根因是**不能直接 import 另一个域文件**（那会让它被加载两遍 —— 见文末「跨文件复用」），
> 所以它自己碰 `winreg`、没有复用 `registry.read`。
>
> ⚠️ **实测记录（CPU 主频）**：`system.hardware` 的 `base_mhz` 来自注册表 `~MHz`，是
> **标称值、不随睿频变化**（本机 i7-12700H 返回 2688MHz，实际可睿频到 4.7GHz）。
> 想知道「现在 CPU 忙不忙」用 `system.load`，不能拿它当实时频率。
> ⚠️ **实测记录**：`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion` 的 `ProductName`
> 在本机返回 `"Windows 10 Home China"`，但实际系统是 **Windows 11**（build 26200）——
> **判断系统版本不能信这个字段**，见 `docs/archive/os-capability-map.md` 的待验证清单。

### 声音 / 外设域

| 原语 | 作用 | 需确认 | 有 dry_run | 块 |
|------|------|:---:|:---:|:---:|
| `sound.beep` | 让电脑**出声**：系统提示音 / 按频率鸣叫 / 播放 wav | 否 | — | 显示与界面 |
| `device.usb_list` | 当前在位的 USB 设备（名字 / 类 / 厂商 / 可移动 / 端口 / 状态） | 否 | — | 外设 |
| `device.printers` | 已装打印机、默认哪台、状态与端口 | 否 | — | 外设 |

> ⚠️ **`sound.beep` 为什么不设确认也不设 dry_run**：它**会出声、会打扰人**，但不破坏数据、
> 不改系统状态，属「低危高频」（同锁屏那一档）。dry_run 是给「做错了会留下后果」的动作踩刹车的。
> 另：`verified` 恒为 `null` —— 系统静音时它会**安静地成功**，「有没有真响」本原语复核不了。
>
> ⚠️ **`device.usb_list` 的噪音口径**：设备树里一多半条目不是「插进来的设备」（根集线器 /
> 接口子项 / 虚拟远程设备）。默认只列真实设备，滤掉多少条写进说明；可移动与否取自设备的能力位，
> **不是猜的**。
>
> ⚠️ **`device.printers` 的「状态」有边界**：状态位是打印后台报的**异常标志**，
> 空 = 没报异常，**不等于一定能打**。默认打印机取自用户配置 —— 实测系统 API 的那个属性位
> 在本机**一位都没置**，只信它会得出「没有默认打印机」这个错误结论。

| `acl.get` | 看文件 / 目录的权限清单：谁能读、谁能改（人话 + 所有者 + 是否继承） | 否 | — | 文件与目录 |

> 走 `ctypes` 调系统底层接口，**不解析命令行的文本输出** —— 那个输出一半稳定一半本地化，

> 改权限的能力**不进原语表** —— 那是能把自己的权限提上去的高危操作。

## ★ 安全约定（三道门）

细节见 `README.md` 的「安全规范」一节，这里只说要旨：

| 门 | 防什么 | 装在哪 | 谁能放行 |
|---|---|---|---|
| **dry_run**（默认 True）| 防**意外 / 测试** | 原语自己的参数 | 调用方自己（传 `dry_run=False`） |
| **PolicyGate**（`requires_confirmation`）| 防**越权** | IR 解释器 | **只有用户能点头**，AI 绕不过 |
| **执行门** | 防**绕过** | `registry.execute()` 入口 | 用户（或接入方的确认器） |

**规则**：
1. **会改变系统状态的原语** → 一律带 `dry_run`，默认 `True`（只预览）
2. 其中**数据破坏 / 不可逆**的 → **额外**加 `requires_confirmation`
3. **只读原语** → 无需 dry_run

> **执行门（2026-09-11 加）**：此前 PolicyGate 只装在 IR 那条路上，`registry.execute()`
> 是裸奔的 —— 平台面板的 /run、脚本直调、以及任何未来的接入方，都能绕过全部安全检查。
> 现在门装在**原语执行器的入口**，任何调用方都得先过；只管会改状态的原语，只读的放行。
>
> **「怎么问用户」是可插拔的**：接入方可以注入**确认器**（读终端、发 IM 消息、
> 等网页点击，各接入方自己定）。不装也能跑，只是无人在场时高危操作会被拒。
>
> ⚠️ 踩过的坑：第一版门以为「stdin 是终端 = 上游会去问」就放行，但**直调场景根本没有
> 上游**，结果既没问也没拦。教训 —— **「有人在」不等于「有人会问」**。
>
> **IR 操作码已精简为 3 个**：`call` / `ask` / `finish`。原来的 `load` / `store` / `search`
> 是与 `call` 重复的别名（且失败时会静默返回参数、不报错），`exec` 则由 `escape` 替代。

> **执行前「一次问清」整批（2026-09-12 加）**：一段计划里常常有好几个要确认的动作，
> 逐条弹会把用户问烦 —— 而「一次交一批活」正是这套系统的卖点。现在解释器在**执行之前**
> 把整批要确认的一次列清（每条给「作用 + 参数」，用原语的说明而不是符号名）、问一次。
> 用户拒绝时**不整段中止**：被拒的那些各自报错，只读的部分照常执行。
>
> ⚠️ **必须由内核来问、内核来记账**：集成功能和接入方都不许自己列清单、自己标记
> 「用户已同意」—— 那等于替用户点头（跟「上游撒谎说问过了」是同一类问题，见上面的执行门）。

⚠️ **开发与测试铁律**：不真实调用接口（只用 `dry_run=True`）。由来见 README。

### 写侧的边界 —— 为什么撤掉了可写白名单

文件域里会改状态的九条（`fs.write` / `fs.append` / `fs.delete` / `fs.temp` / `fs.copy` /
`fs.move` / `fs.mkdir` / `fs.attrs` / `fs.link`），边界是**两道**而不是三道：

| 层 | 管什么 | 现在怎么配 |
|---|---|---|
| `dry_run` | 防**误触**（默认只预览） | 九条都带（`fs.attrs` 只在「改」那半边），默认 `True` |
| `requires_confirmation` | 防**越权**（要用户点头） | `write` / `append` / `delete` / `copy` / `move` / `link` 带；`fs.temp` / `fs.mkdir` / `fs.attrs` 不带 |
| ~~可写白名单~~ | ~~限制可触达的位置~~ | **已撤除**（2026-09-11）。留着的是**系统禁区**硬拒：盘根 + `Windows` / `Program Files` / `ProgramData`，源和目标**都要**判 |

**当初为什么加**：怕 AI 被诱导着把文件复制/移动到奇怪的地方（往启动目录塞东西、覆盖系统配置）。

**为什么又撤**：
1. **拦不住前两层没拦住的**。前面已有 dry_run 和确认机制，白名单只是叠在两道关卡后面的
   第三道，防的是同一件事 —— 而破坏性更强的 `fs.write` / `fs.delete` 反倒从来没有过它。
2. **它连「源」也管，而源只是被读**。`fs.read` 本来就能读任意位置，限源一点安全性都没增加，
   只是让原语在真实场景里直接没法用 —— 项目目录里的文件当源都被拒。
3. **硬拒没有商量余地**。「确实要操作别处」时彻底没辙。

**真正的取舍**：白名单要做对，就不该是「禁止名单」，而该是「需确认的边界」（白名单内免问、
出了白名单才问）。那需要 core 支持「按参数决定要不要确认」—— 而现在的 `requires_confirmation`
是**按原语**声明的静态开关，看不到参数。为这点收益去动安全内核，不划算。

**代价（如实记）**：撤掉之后，`fs.copy` 能把任意位置的文件搬到任意位置（系统禁区除外）。
但这没有增加新的泄露面 —— `fs.read` 本来就读得到；而且这些动作现在都要用户点头。

### 解压的两道防线

`archive.extract` 是本项目**安全增量最大**的一条。压缩包是**不可信输入** —— 里面的文件名
会被变成磁盘上的路径，而这个转换过程有两条经典攻击路径：

| 攻击 | 怎么打 | 怎么防 |
|---|---|---|
| **路径穿越** | 成员名里带 `..` 层层往上跳，解出来就跑到目标目录**外面** | **每一条成员**先规范化、确认落点在目标目录**之内**；任一条不合法就**整包拒绝**并指名是哪一条 |
| **压缩炸弹** | 65KB 的包解出来 64MB（本机实测比值 1027:1），撑爆磁盘 | 解压后**总体积**与**文件数**两道上限 + 压缩比异常检测；判定用成员**声明**的大小，真解压时再按**实际写出的字节数**兜第二道 |

**为什么不「跳过坏的、解好的」**：部分成功最难排查，而且攻击包往往靠「好的那几条」
把调用方的注意力引开。**整包拒绝**是这里有意选的方向。符号链接 / 硬链接成员一律拒绝 ——
它们能把后续成员引到目录外。

> **实测（2026-09-12）**：构造了一个成员名带往上跳两级的包，工具**整包拒绝**；
> 逃逸文件没有落地、连目标目录都没被创建。另有一个真·高压缩比包（64MB 全零压成 65KB）
> 被压缩比检测拦下。

### 中文名的乱码 —— 规范没人遵守，只能猜

zip 规范要求「成员名含非 ASCII 就设 UTF-8 标志位」，但**现实里一堆包不设**，于是 Python
一律按 cp437 解，中文名全成 `▒¿╕µ.txt` —— 看目录看不懂，**解出来落盘也是乱码名**。

而不设标志位的包还有**两类，存的编码不一样**（本机实测）：

| 来源 | 存的是什么 |
|---|---|
| 老工具（旧版 WinRAR、部分国产软件） | **GBK** 字节 |
| Bandizip 7.37 | **UTF-8** 字节 |

所以只能在这两者之间猜 —— 而**判据不能是「解得通」**：GBK 几乎什么字节都能解
（`fs.read` 里那条经验在这儿同样成立），「报告」的 UTF-8 字节按 GBK 解是「鎶ュ叡」，
解得通、但是错的。做法是两种都解一遍、**挑更像正常文件名的那个**（画框 / 方块 /
希腊字母扣分，汉字加分），**并且把「保持原样」也列为一个候选** —— 默认本来就对时不该乱动。

> **实测（2026-09-12）**：GBK 包、Bandizip 式包（UTF-8 无标志）、标准包三种都试过，名字还原
> 全部正确，且 `archive.list` 看到的名单与**解压落盘的名字一致**（两边走同一套判定）。
> **Bandizip 自己反而认不出** GBK 包 —— 它解出来的是 `���ı���.txt`（按 UTF-8 硬解到底）。
> 所以这条不是「追平 Bandizip」，是**比它做得对**。
>
> 顺带：**tar 没这个问题**（tarfile 按 UTF-8 / pax 处理），这套只用在 zip 侧。

### 跟 Bandizip / 7-Zip 的能力对照

| 能力 | 本库 | 说明 |
|---|---|---|
| 中文名不乱码 | ✅ 能正确还原 | 见上节 —— Bandizip 认不出 GBK 包 |
| 智能解压（`auto_folder`） | ✅ | 语义与 Bandizip 的 `-target:auto` **实测对齐**：顶层项只有 1 个就不套、2 个及以上才套（单文件包也不套） |
| 路径穿越 / 压缩炸弹两道防线 | ✅ 独有 | 见上节；外部工具不会做得这么细 |
| 7z / rar / iso / zipx / lzh | ❌ **不做** | 零依赖只用 stdlib 是硬约束。但**认得出**，会直接说是哪一种、该拿什么工具开 |
| 分卷包（`.z01` / `.001` / `.part1`） | ❌ **不做** | 同上；而且会点明「单卷解不开」，不报「文件已损坏」这种误导性结论 |
| 加密包 | ❌ **不解密** | 预览阶段就报 `encrypted_count`，不等到真解压才炸 |

### 出网的边界 —— 网络域那两条为什么两道保护都上

`net.http_get` / `net.download` 是本项目里**唯一会主动对外通信**的原语（别的原语最多读本机、
或跟目标握一次手）。它们同时踩两条风险线：**数据外泄**（请求头 / 体 / URL 都会被送到外部）
与**落地文件**（后者会把外部内容写进本地磁盘，等于能落一个可执行文件下来）。

| 层 | 防什么 | 怎么配 |
|---|---|---|
| `dry_run` | 防**误触** | 默认 `True`：`http_get` 预览**一个字节都不出网**；`download` 预览**不联网也不写盘** |
| `requires_confirmation` | 防**越权** | 两条都带，走 PolicyGate + 执行门 |

另外三条硬边界写死在原语里：① **只支持 http/https**（挡掉本机文件协议 —— 那能直接读本机文件，
等于绕过文件域的全部判定）；② 响应体**有大小上限**（不设上限的话，一个链接就能撑爆上下文）；
③ 下载**先写临时名再原子改名**（中途断了正式文件根本不存在，不会留一个看着正常的半截文件）。

## IR 调用示例

```json
{
  "instructions": [
    {"op": "call", "tool": "system.info", "args": {}, "out": "sys", "depends_on": []},
    {"op": "call", "tool": "fs.list", "args": {"path": "./"}, "out": "dir", "depends_on": []},
    {"op": "call", "tool": "disk.list", "args": {}, "out": "disks", "depends_on": []},
    {"op": "finish", "args": {}, "depends_on": ["sys", "dir", "disks"]}
  ]
}
```

> 前三条**互不依赖 → 并行执行**；`finish` 等三条全部回来才收尾。
> 这就是「一次交一批」的实际样子 —— 把本来要来回三次的调用，压成一次。

### `$引用` —— 用上一步的结果

在参数里写 `"$寄存器名"` 或 `"$寄存器名.字段名"`，就能取到前面某条指令的输出：

| 写法 | 含义 |
|---|---|
| `"$sys"` | 整个寄存器 —— 前一条指令的输出对象 |
| `"$sys.platform"` | 取其中一个字段（`system.info` 返回 `platform` / `machine` / `total_mb` / `avail_mb`） |

⚠️ **两条硬规则**（写错**不会报错**，只会把那段文字原样传下去，很难查）：

1. **整个字符串必须就是引用本身** —— `"$sys.platform"` ✅ ／ `"平台是 $sys.platform"` ❌
   （后者是**拼接**不是引用；要拼就交给工具自己做）
2. **取字段用点号** —— `$sys.platform` ✅ ／ `$sys['platform']` ❌

> 引用了不存在的寄存器（名字拼错）**会在执行前被静态校验拦下**，并指出是哪条指令 ——
> 这是写 IR 时最常见的一类错。

```python
# 执行单个原语（走原语工厂）
import sys; sys.path.insert(0, ".")                    # 项目根
from core import factory
factory.load_primitives("primitives")
factory.registry.execute("system.info", {})            # 只读，直接跑
factory.registry.execute("fs.delete", {"path": "..."}) # dry_run 默认 True → 只预览
```

```bash
# 命令行入口（adapters/cli.py）—— 给 bash 脚本、以及任何语言写的程序用
python adapters/cli.py list process                     # 册子里有什么
python adapters/cli.py describe process.find            # 一条原语怎么调
python adapters/cli.py call process.find --args '{"pattern": "rag-daemon.py"}'
python adapters/cli.py call process.find --args-file q.json   # 查进程推荐用这个：查询词不进命令行
python adapters/cli.py run ir.json                      # 跑一段 IR（或 run - 从 stdin 读）
```

> ⚠️ **查进程时为什么推荐 `--args-file` / `--args -`（stdin）**：查询词写在命令行里，
> 执行这条命令的 shell 自身也会被 `process.find` 命中 —— 因为**它的命令行确实含这个词**。
> 这是真匹配不是误报，但会让结果多出几条杂音。把词从命令行挪进文件或 stdin，结果就干净了。
> （`proc-find.sh` 当初把 pattern 放进环境变量，是同一个道理。）

> **stdout 只放结果 JSON** —— 可直接接 `jq`，不用剥任何前缀；错误与提示一律走 **stderr**。
> 退出码：`0` 成功 / `1` 执行失败 / `2` 用法错误 / **`3` 被安全门拒绝**。
>
> `3` 单独占一个码是有意的：脚本必须分得清「**没查到**」和「**被拦住**」——
> 把两者混成同一个「失败」，正是那些「检查脚本坏了却报一切正常」的病根。

> ⚠️ 发给 LLM 时原语名会转成下划线形式（`system.info` → `system_info`），因为 API 规定函数名只能含字母数字下划线。解释器入口会自动还原。

## 怎么把它接进你的 Agent（集成模式）

推荐的做法**不是在 Agent 循环里一条条手动调原语**，而是在你的 Agent 与 IntentOS 之间加一层「计划工具」——
Agent 把「一堆有依赖的操作」一次写成 IR 交给它，执行完把结果带回来：

```
你的 Agent 检测到「多步系统操作」
   │  harness 层判断（代码，不靠 LLM 自觉）
   ▼
调用计划工具（如 exec_plan）→ 交 IntentOS 执行 → 返回结果
```

好处：

- **中间层独立**：不内联进你的 Agent 循环，OS 原语全在 IntentOS 里，谁要用都插同一个桥
- **主动引导**：该走计划路径时由**代码**决定，不依赖 LLM「积极调用」
- **安全不丢**：高危原语在 IntentOS 内标了 `requires_confirmation`，走桥同样触发 Policy Gate

> 参考实现见 `adapters/example_agent.py` —— 最小可运行示例，clone 下来直接跑。

## 分层与边界

- **内核**：IR 协议 + 解释器 + Policy Gate + 审计 → `core/`
- **内置系统原语**：按域分文件 → `primitives/`（`system.py` / `process.py` / `fs.py` / `disk.py` / `event.py` / `power.py` / `service.py` / `net.py` / `ui.py` / `registry.py` / `startup.py` / `env.py` / `task.py` / `archive.py` / `shell.py` / `acl.py`，外加 `escape.py` 逃生舱）
- **外设**（可插拔）：你的 Agent 自带的工具（`source="agent"`，同名时优先于内置原语），见 `adapters/example_agent.py`
- **留给 escape / 插件**：ffmpeg、数据库、浏览器自动化这类重（参数空间大 / 语义复杂）
  > `exec` 操作码 2026-09-11 已删除，它的职责由 `escape` 原语承担（独立子进程 + 每次确认）。

> **原则**：中间层提供"操作系统的最小能力集"，复杂工具通过 escape / 插件接入。
> **加新 OS 能力 = 在 `primitives/` 下按域建个文件，写一个 `@declare_primitive(...)`** —— 自动登记 + 自动显示，核心零改动。

> **什么不该做成原语**：超出「本机 × 单次 × 无状态 × 不解释语义」的需求 ——
> 云端服务、跨应用驱动、需要历史/累计、需要读懂内容（xlsx / PDF / 图片）—— **一律不做成原语**，
> 那是上层的活。判断标准与各自的去向见 README 的「能力边界」一节。
> 另有一类**不是做不到、而是有意焊死**的（注册表自启动键禁写、`startup` 只给看不给改、
> `ui.type_text` 只做纯文本不留组合键），碰到这类需求走 `escape` 或交由上层，通常比在原语里放开权限更稳妥。

### 跨文件复用：共享的东西放 `_common.py`

**不是「每个域文件必须自包含」** —— 那是 2026-09-11 更正前的旧说法。真实情况分两层：

- **不能用动态模块名互相 import**：`factory.load_primitives()` 用独立模块名
  （`prim_<文件名>`）加载，而且**不塞进 `sys.modules`**，所以 `import prim_fs` 这类写法必然失败。
  旧说法「不能互相 import」就是从这儿来的。
- **但按包路径 import 完全可行**：`primitives/` 是个正常的包（有 `__init__.py`），
  `from primitives._common import ...` 走标准 import 机制，**已实测可用**。

⚠️ **别直接 import 另一个域文件**（哪怕走包路径）—— 那会让它被**加载第二遍**
（一次叫 `prim_xxx`、一次叫 `primitives.xxx`），模块级代码跑两次。登记表是「先到先得」，
重复登记本身不出错，但白跑一遍，而且将来若有人在模块级写了有副作用的代码就会出事。

**正解**：跨域复用的工具与常量放 `primitives/_common.py` —— 文件名以 `_` 开头，
`load_primitives()` 扫描时会跳过它（`if p.name.startswith("_")`），不会被当成原语加载。
各域文件 `from primitives._common import ...`，**只加载一次**。

目前共享的有：外部命令输出解码、管理员权限探测、注册表类型名、服务启动类型表、
计划任务 XML 命名空间与取节点文本，以及**路径安全地基**（规范化 / 包含判定 / 系统禁区判定 /
重解析点判定 —— 2026-09-12 从文件域、归档域、快捷方式域的三份拷贝收敛成一份）。

> ⚠️ **一条给新原语的规矩**：**凡是遍历目录树的地方**（数大小、复制、删除、打包、搜内容），
> **必须**用 `is_reparse_point()` 剪掉符号链接 / 目录联接。原因 —— `os.walk` **不会**自动跳过它们
> （实测：目录联接的 `islink()` 返回 False，walk 照样递归进去）。一个指回祖先的目录联接
> 能让遍历绕圈：轻则同一个文件被数两遍，重则转到撞上文件数上限。
> **这个坑的性质是「不知道它存在的人一定会踩」**，所以写成规矩留在这里。
