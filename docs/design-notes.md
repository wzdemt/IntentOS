# 设计札记 —— 为什么长成这样

> README 讲「它是什么、怎么用」；这一份讲「**为什么是现在这样**」。
>
> 这里记的是**取舍过程**：当时权衡了什么、试过什么、为什么又撤了。
> 只想用 IntentOS 的话，读完 README 就够了 —— 这份是给想改它、或者想质疑它设计的人看的。

---

## 一、核心理念：只负责执行，不负责理解

```
调用方（任何 Agent）──写出──▶ IR(语义指令序列) ──交给──▶ 本地确定性执行 ──▶ 结构化结果
       ▲                                                                        │
       └────────────────── 结果回填，Agent 决定下一步 ──────────────────────────┘
```

- **IR 由调用方生成**：怎么把用户意图翻译成 IR（靠 LLM、靠固定模板、靠手写）是调用方的事，IntentOS 不关心、也不掺和。
- **IntentOS 是执行引擎**：把 IR 路由到预写好的确定性函数，负责校验、并行、`$引用` 传值、安全闸门。
- **一次交一批，比一步步问快得多** —— 把工作量从「贵的推理侧」挪到「便宜的本地执行侧」。

这条分工是后面所有设计的根：**只要守住「不解释语义」，内核就能一直薄**；一旦开始理解语义，它就会长成一个 Agent 框架 —— 那是另一个东西了。

---

## 二、能力边界（为什么划得这么紧）

一句话：**IntentOS 的能力面 = 本机 × 单次 × 无状态 × 不解释语义。**

这不是「还没做」，而是**按设计不打算覆盖**。超出这四维的需求，请由上层（Agent / skill / 调用方库）自己补。
把这条写明白，是为了**别让上层反复试探同一面墙** —— 2026-09-12 拿四组真实场景实测过，
六个跨出这四维的需求，全部撞在这一处。

| 维度 | 做得到 | 不做 | 该谁做 |
|---|---|---|---|
| **本机** | 进程 / 文件 / 端口 / 窗口 / 服务 / 注册表 … | 云盘同步、发邮件、调第三方 API | 调用方，或走 `escape` 逃生舱 |
| **单次** | 一次调用进出，答「此刻是什么」 | 累计、趋势、历史、「上次同步到哪了」 | 调用方自己采样、自己维护状态 |
| **无状态** | 不持有会话 / 凭据 / 调度 | 登录态、双向同步、长任务编排 | 上层 skill / Agent |
| **不解释语义** | 取字节、写字节、算哈希 | 读懂 xlsx / PDF / 图片里写了什么 | 上层（格式理解交给专门的工具） |

**还有一类要单独说明**：有些不是「做不到」，是**有意焊死的门** ——
注册表自启动类键一律禁写、`startup` 只给看不给改、`ui.type_text` 只做纯文本不留组合键、
`archive.extract` 拒符号链接。这类需求**功能上离得很近却做不成**，是**风险分级的结果**。
遇到时**不要试图绕过**（比如顺手放开写权限），应改走 `escape`、或交由上层承担，并把风险讲清楚。

**「关掉某个自启动项」是评估过的、决定不做的**（2026-09-12）：能安全覆盖的只有注册表那 23 条，
而**那部分用户自己开任务管理器 30 秒就能关**（任务管理器的「禁用」采用的正是可逆的标记机制）；
真正难关的服务类（138 条，抽样全是 Windows 系统服务）**不该开放**。
等于「做的部分是用户已经能轻松做的，不做的是真正难、但也不该做的」——**Agent 在这里的增量价值极小**，
为此加一条带确认门的高危原语不划算。**若将来出现「装机批量清理」这类场景，再单独评估。**

**为什么把边界划得这么紧**：执行层薄一点，安全面和可预测性就高一点。
`escape` 是这条边界上的**正式出口** —— 它带门卫（每次执行都要用户点头），
存在的意义正是让「想绕开 IntentOS 的人」有一个**可见**的入口，而不是在围栏上自己开洞。

## 三、接入形式怎么选（以及为什么没做 MCP server）

**先说 IntentOS 提供什么** —— 这几条是并列的，不是只有「快」：

| 价值 | 说明 |
|---|---|
| **稳定** | 同一套原语接口，底下是 PowerShell / ctypes / CIM，调用方不用管；系统的坑在层内消化掉 |
| **安全** | Policy Gate + 执行门 + `dry_run` 默认预览 + 路径禁区，**硬编码在解释器里**，不靠模型自觉 |
| **结构化** | 返回 JSON，不是需要二次解析的文本 |
| **可组合** | 98 条原语能拼装（`skills/` 就是组合出来的能力） |
| **可嵌入** | 无状态、不持有 session，任何 Agent 都能用 |
| **省** | 一次交一批、DAG 并行，减少模型往返 |

前五条**跟快慢无关** —— 哪怕一段 IR 里只丢一个调用，稳定 / 安全 / 结构化这些价值照样成立。

**选接入形式时，判据是「能不能完整保住这些价值」**，其中权重不同：
**效率损失是「慢一点」，安全损失是「出事了」** —— 任何会绕过执行门的接入形式，直接出局。

| 形式 | 开销 | 通用性 | 需要什么基础设施 |
|---|---|---|---|
| 进程内嵌入（Python 库） | 几乎零 | 只有 Python Agent | 无 |
| **CLI**（← 本项目的选择） | 0.26 秒/次 | 任何语言（subprocess） | 无 |
| HTTP 常驻服务 | ~1 毫秒 | 任何语言 | 要起服务、管端口、管生命周期 |
| MCP 单工具 | 协议开销 | MCP 生态 | 要配置、要握手 |

**为什么 CLI 是最优**：

- **零基础设施** —— 不起服务、不配协议、不管端口
- **任何语言都能用** —— `subprocess` 调一下，stdout 直接是 JSON
- **天然就是「一次交一批」的形状** —— 读一段 IR、输出结果、退出
- **不用常驻** —— 用完就走，不残留状态（跟本项目的「无状态」本性正好合拍）
- **0.26 秒的开销在 Agent 场景里可忽略** —— 实测：加载 98 条原语 0.24s + 执行 0.03s；
  而模型一次往返是 1~10 秒。**用 0.26 秒换掉一次 1~10 秒的往返**，这笔账划算几十倍

**为什么不做 MCP server**：MCP 的协议形状是「一次一个工具调用」。把它铺成 98 个 OS 工具，
就退化成「又一个 OS 工具集」，而且每条调用都要过一次模型往返 —— **效率优势被协议抹平**。

> 要接 MCP 的话，**正确姿势是只暴露一个工具**（接收整段 IR、一次执行完返回）——
> 既不丢 IR 的形状，又能进 MCP 生态。**等真有人需要再加**，现在不为「可能的用户」背复杂度。

## 四、安全设计：为什么是硬编码而不是提示词

**Policy Gate 不靠模型自觉**。高危确认、执行门、路径禁区判定全部写死在解释器里 ——
因为「靠 prompt 提醒模型别干坏事」这件事，**在提示注入面前没有防线**。

**执行前「一次问清」整批**：要确认的动作不在执行途中逐条弹，而是执行前一次列清、点一次头；
拒绝时**不整段中止**，只读的部分照常执行 —— 这比「一个不批就全不干」更接近用户的真实意图。

**`dry_run` 默认 `True`**：所有会改变系统状态的原语，默认只预览不执行。
这不是「多一道手续」，是**默认值的选择** —— 默认安全，要动手得显式说出来。

**开发与测试铁律**：设计和开发阶段**不真实调用**会改状态的接口，一律 `dry_run=True` / mock。

> **由来**：2026-09-10，`power.lock`（当时无 `dry_run` 保护）在测试中被真实调用，
> 导致用户屏幕被锁。此后定为铁律。

## 五、设计定位

- **不做另一个 Agent 框架**（那是红海），做**可嵌入的执行引擎**——任何 Agent（含 MCP）通过 IR + 上下文即可用。
- **内核 / 外设分离**：IR 协议、解释器、Policy Gate 是通用内核；工具集是可插拔外设（agent 自有工具优先）。
- **最终目标**：在硬件全面升级（存算一体 / AI 原生 OS）前，用 agent 增强管理 OS——IntentOS 是第一步的执行引擎。

---

## 缘起

这套设计不是从零起意的：先有了「**把执行从推理侧剥离出去**」这个判断，
才倒推出「需要一层什么样的东西来接住它」—— IR 协议、确定性执行、硬编码的安全门，都是从这个判断长出来的。
