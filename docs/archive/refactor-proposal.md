# IR 层重划与安全边界调整 —— 改动提案

> 📅 2026-09-11 ｜ 状态：**改动 1–6 已实施并验证；改动 7 待做**
> 起因：一次围绕「IR 是否必要 / `exec` 是否该留 / 安全门该装在哪」的设计讨论，结论需要落成可执行清单。
>
> **实施后**：核心结论已沉淀进 `docs/os-primitives.md` 的「安全约定（三道门）」与「逃生舱」两节。
> 改动 7 做完后，本提案移入 `docs/archive/`。

---

## 一、一句话

IR 这层**该留**——并行调度、`$引用` 传值、静态校验是真价值，function calling 给不了。
但**该瘦身**：砍掉一半操作码，把安全门从「解释器里」挪到「原语入口」，
把「原语覆盖不到」从「偷偷开个洞」改成「一扇**有门卫的门**」。

---

## 二、改动速览

| # | 改动 | 性质 | 动到哪 |
|:-:|---|---|---|
| 1 | 砍 `load` / `store` / `search` | 删冗余 | `core/interpreter.py` |
| 2 | **删掉** `exec`（原方案是降级，实施时改为直删） | 关后门 | `core/interpreter.py` |
| 3 | 补 `ask` 的真实交互 | 补半成品 | `core/interpreter.py` |
| 4 | 新增逃生舱原语 `shell.run` | 加能力（高危） | `primitives/` |
| 5 | 安全门下沉到 `registry.execute()` | **补漏洞** | `core/interpreter.py` + `core/factory.py` |
| 6 | 加厚「确认」这道关 | 新增 | `core/interpreter.py` |
| 7 | 原语错误处理规范 | 补欠账 | `primitives/` 逐个 |

**操作码：7 → 3**（`call` / `ask` / `finish`）

> **实施时的调整**：改动 2 原方案是「保留 `exec`、加锁降级」，落地时改成**直接删掉**——
> 因为逃生舱已统一由 `escape` 原语承担（09-11 定），再留着 `exec` 就是**两个出口**，
> 等于白合并。删掉后 `call` / `ask` / `finish` 之外什么都不剩，最干净。

---

## 三、逐项说明

### 改动 1 · 砍掉 `load` / `store` / `search`

**现状**：这三个 op 在解释器里是**硬编码映射到三个特定工具**——

```
load   → read_file
store  → write_file
search → search_memory
```

**问题**：
1. **纯冗余**——既然有 `call`（"调用任意已注册工具"），这三个就是个别名。作者自己在系统提示里也写了：「`call`：**绝大多数任务都该用它**」
2. **静默失败**（真 bug）——工具不存在时，它们**原样返回参数、不报错**。调用方会以为执行成功了
3. 模型要记 7 个操作码该用哪个，是纯负担

**改法**：从操作码枚举里删掉三个，统一走 `call`。

**代价**：模型若仍输出 `load`，静态校验会报「非法操作码」→ 打回重写。可接受。

---

### 改动 2 · 降级 `exec`（保留，加锁）

**现状**：允许模型写一段 Python 直接跑，靠「受限内置函数」拦着——而且**它现在是个普通操作码，模型想用就用，跟调一个只读原语一样容易**。

**问题**：
1. **它是绕过整个中间层的口子**——有它在，原语体系那套「安全」就打了折
2. **门卫管不到它内部**——PolicyGate 管的是「这条指令准不准执行」，代码跑起来之后干了什么，完全在视野外
3. **「受限」挡不住有心人**——Python 里任何对象都能顺着类型族谱往上摸到语言底层，全程不用任何被禁的东西
4. 最要紧的是第 1 条的**后半句**：它跑起来**毫不费力**，没有任何摩擦

**改法**（2026-09-11 定：**保留，但降级**）：
- 标 `requires_confirmation` → 每次执行**必须用户点头**
- 从「普通操作码」降为「**逃生舱**」，跟 `shell.run` 归为同类
- 系统提示与手册里写明：**先想原语，原语不行才用它**

**为什么不全删**：留一个「册子上没有的加工」的出口，比逼着用户绕开 IntentOS 自己敲命令要好。

**代价**：围栏上留了一个洞——**锁上了，但它还是个洞**。安全兜底压在「用户会认真看确认」上，所以改动 6 不是可选项。

---

### 改动 3 · 给 `ask` 补上真实交互

**现状**：`ask` 返回 `{"question": …, "answered": None}`——**没有任何人去问用户**，空壳。

**为什么不能直接删**：改动 4 的逃生舱正需要它——「原语覆盖不到 → 问用户 → 用户点头才走原生操作」。这是这套设计里**唯一的对外沟通口**。

**改法**：参照 `PolicyGate.confirm()` 已有的做法（读标准输入、非交互环境拒绝），补上真实的问答。

**代价**：无。

---

### 改动 4 · 新增逃生舱原语 `shell.run`

**背景**：IR 路线的安全来自「能力有限」，而「能力有限」意味着「干不了的事很多」。现在的原语只有 22 个，Windows 有几千条命令。**覆盖不到的需求怎么走**？

**设计**（2026-09-11 定）：

```
模型发现原语覆盖不到
        ↓
   用 ask 问用户：「这件事册子上没有，我需要跑一条原生命令，可以吗？」
        ↓
   用户点头 → 执行，且留记录
   用户拒绝 → 放弃
```

**关键**：逃生舱**不是破洞，是一扇有门卫的门**——
- 它是一个**正经原语**（`shell.run`），登记在册、出现在面板上、有审计
- 标 `requires_confirmation=True` → 必须用户点头
- **绝不允许模型自己决定走它**

**边界**（2026-09-11 定）：**接受完整命令字符串**——想跑什么写什么，跟现在的 Git Bash 体感一致。

**代价**：多一条高危原语要维护；命令串里若含拼接、重定向、通配符，**安全兜底就落在「用户认真看确认」上**（见改动 6）。

---

### 改动 5 · 安全门下沉到 `registry.execute()` ⚠️ **这是漏洞**

**现状**：PolicyGate 只装在 IR 路径上（`SemanticInterpreter` 里）。

**用大白话说**：门卫只管「走 IR 这条走廊的人」。**其他走廊没有门。**

现成的两条裸奔路径：

| 路径 | 现状 |
|---|---|
| `registry.execute(名字, 参数)` 直接调用 | **零检查**——连 `requires_confirmation` 都不看 |
| 平台面板的「运行」按钮（`/run`） | 只看 `requires_confirmation`，且是**直接拒绝**而非询问 |

**这意味着**：今天测原语时走的就是第一条路。因为是只读的所以没事——但**换成删除文件，一样是直接删，没人拦**。

**改法**：给 `ToolRegistry` 加一个**执行门**（`ExecutionGate`），由工厂在装配时注入（避免 `core` 内部循环依赖）：

```
registry.execute(name, args)
      ↓
  执行门（装了才检查）
      ├─ 只读 / 未登记策略      → 放行
      ├─ 上游已确认（IR 路径）   → 放行，不重复问
      ├─ 有确认器 → 用它问      → 读终端 / 发 IM 消息 / 等网页点击
      ├─ 无确认器 + 在终端      → 门自己读终端问
      └─ 真没人可问             → 拒绝
      ↓
  真正执行
```

这样不管谁调——IR 解释器 / 平台面板 / 随便一个脚本——**都得先过门**。

**「怎么问用户」必须可插拔**（2026-09-11 定）：
`sys.stdin.isatty()` 是**终端思维**。QQ 那头的用户明明就在，只是不在终端里——
用终端判断会把他和「真的没人」当成同一种情况，一刀切拒绝。所以确认动作抽象成
`confirmer` 回调，由接入方注入。

⚠️ **实测踩到的坑（2026-09-11）**：第一版门以为「stdin 是终端 = 上游会去问」就放行了，
结果**直调场景根本没有上游**，变成既没问也没拦。教训：**「有人在」不等于「有人会问」**。

**范围**（2026-09-11 定）：**只管会改状态的原语**。只读的（查进程、看磁盘、读注册表）直接放行——拦了没意义，还每次多一道手续。

**代价**：接入方要记得装确认器（不装也能跑，只是无人在场时会被拒）；IR 路径多传一个 `confirmed=True` 标记。

---

### 改动 6 · 加厚「确认」这道关

**为什么单列一条**：改动 2 和改动 4 把安全兜底**都压在了「用户点头」上**。这道关的质量，直接决定那两项改动是「安全加固」还是「自欺欺人」。

**要求**：
- 确认时**完整显示**要跑的东西，**不许截断**（命令长了要能翻看全文）
- 尽量**翻译成人话**一起显示——「将删除 D:\照片 下的 3 个文件」比一行 `rm` 有用得多
- 非交互环境（QQ / 微信 / CI）**一律拒绝**，不许自动放行
- 用户拒绝后**优雅回退**——告诉模型「用户不同意」，而不是抛异常崩掉

---

### 改动 7 · 原语错误处理规范

**背景**：已知欠账——`process.kill` 真执行时**不看返回码就报成功**。改动 1 的静默失败也是同一类毛病。

**改法**：定一条规矩并逐个补齐——
> 会失败的动作，**必须把失败如实反映在返回里**，不许「发出去了就算成功」。

## 三点五、顺带清掉的尾巴

实施过程中顺手做掉的（不在原提案里）：

| 项 | 情况 |
|---|---|
| **`system.uptime` 归位** | 一个**真实注册的原语**却住在 `core/factory.py` 里，挂着「示例」的名头 —— 是「加能力不碰 core」那条铁律的**唯一反例**。已挪到 `primitives/system.py`，顺手修准两处：uptime 改用 `GetTickCount64`（不再依赖 `time.monotonic()` 那个「未指定」的起点）、`boot` 字段改为真正返回**启动时刻**（原来返回的是主机名，名不副实）。搬完 `core/` 下原语注册数 = **0** |
| **核心瘦身** | `LLMClient` / `AgentRuntime` / `MockLLM` / `DEFAULT_SYSTEM_PROMPT` / `build_default_registry` / `build_ir_tools` 全部移出 —— 见下面「改动 8」 |
| **文档分家** | docs 从 5 份重叠的 → 手册 + 自动生成看板 + 归档区 |

### 改动 8 · 核心瘦身（实施中追加）

**起因**：一个关键判断 ——「IntentOS 不是 agent，只是其他 agent 能够调用的中间层，本质上只是个工具」——
而代码顺着「示例」一路长出了一个 Agent 运行时，与 README 自己写的「不做另一个 Agent 框架」相矛盾。

**改法**：`core/` 里只留「协议 + 执行 + 安全 + 工厂」；LLM 客户端、Agent 循环、提示词、
内置演示工具全部移除。`interpreter.py` **838 → 550 行**，演示改为**手工构造 IR → 交给解释器**。

**代价**：删掉 `adapters/httpx_llm.py`、`examples/real_api.py`、`examples/cleanup.py`。
接入方要用 LLM 生成 IR，自己接（`IR_TOOL_SCHEMA` 仍保留，它是协议的一部分）。

## 四、建议执行顺序

| 步 | 做什么 | 为什么这个顺序 |
|:-:|---|---|
| 1 | **改动 5**（安全门下沉） | 修漏洞优先，且它是后面所有改动的安全底座 |
| 2 | **改动 1**（砍三个 op） | 纯删除，风险最低，立刻减少模型的学习负担 |
| 3 | **改动 2**（砍 exec） | 依赖 1 完成后再删，避免一次动太多 |
| 4 | **改动 3**（补 ask） | 改动 4 的前置 |
| 5 | **改动 4**（逃生舱） | 需要 3 和 5 都就位 |
| 6 | **改动 6**（错误规范） | 长期活，随砌原语一起补 |

## 五、已定的取舍（2026-09-11）

| 问题 | 决定 |
|---|---|
| 砍掉 `exec` 后「随手算一下」怎么办 | **保留 exec**，降级成「必须用户点头」的逃生舱 |
| 逃生舱的边界收到哪一层 | **接受完整命令字符串**，跟 Git Bash 体感一致，靠确认兜底 |
| 安全门要不要管只读原语 | **只管会改状态的**，只读的放行 |

**三条的共同取向很清楚：实用优先，安全兜底压在「用户点头」上。**

⚠️ **由此带出一个必须正视的后果**：改动 2 和改动 4 现在其实是**同一个东西的两副面孔**——
`exec`（跑 Python）能删文件、能起进程，`shell.run`（跑命令）也一样能。
**等于围栏上留了两个口子**，都锁着，但都是口子。

**所以改动 6 不是锦上添花，是这三条决定能不能成立的前提。**
