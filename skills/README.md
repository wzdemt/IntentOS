# skills / 任务级能力

> IntentOS 的「能力」层。与 `primitives/`（底层系统原语）分层：
> **原语是原子操作（可执行 / 可审计），skill 是把几条原语交叉成「一件事的完整答案」。**

## 定位

| | primitives/ | skills/ |
|---|---|---|
| 粒度 | 原子操作：读 / 写 / 列 / 删 | 组合能力：交叉几条原语 + 一套判据，回答「一件事」 |
| 例子 | `process.list`、`fs.stats` | 「谁在偷跑」= 进程 × 自启 × 网络连接 × 归因判据 |
| 谁执行 | 解释器按名调用，进 registry，可审计 | 一次调用；**不进 registry**、不占原语名额 |
| 判据 | 无 —— 原语只负责如实取数 | **有** —— 什么算异常、怎么归因，固化在代码里 |

## 为什么是「可执行的一次调用」，不是「一份说明」

接入测试实测过：给 agent 一份说明书让它照着调原语，**成本比不给还高** ——
读说明 + 按说明逐条探索，比它拿原生工具自己干更贵。省法只有「**一次任务一次调用**」：
把组合逻辑固化在代码里，agent 不必每次重想。

所以 skill 是**代码**，不是文档。

## 怎么加一个 skill

1. 在 `skills/` 放一个 `.py` 模块，导出 `detect(**kwargs)` 或 `run(**kwargs)`
2. 内部用 `registry.execute("原语名", {...})` 调原语（走同一条 journal + 安全门）
3. 返回一份能直接读的结构化结论，附上判据依据（让人能复核，而不是只给个结论）
4. 调用：`python adapters/cli.py skill <模块名> --args '{"...": ...}'`

**设计时要守住的一条**：判据必须**自适应**，别写死「某台机器上怎样算正常」。

> 反面教材（写 `proc_detective` 时真踩过）：「路径不在 Program Files 就可疑」。
> 实测本机 49 个进程装在 D 盘自建目录，**全是用户自己的软件**（VS Code / QQ / Git /
> Python），这条判据 100% 误报；而「路径在 Temp / 下载 / 盘根」命中 0 个。
> 换成「这个进程是谁拉起来的」（父进程归因）才自适应 —— 换台机器照样成立。
